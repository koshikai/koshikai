## 稼働中の自動化

自宅の LXC で常駐しているエージェントに任せているのは、定型の確認と実行です。いま動いているのはこの 4 つ。

- 毎日 02:30 に、会話ログ・記憶・スキル・スケジュールを暗号化して退避する
- push のあと CI の結果を待ち、失敗していればログを読んで原因を報告する
- ファイルを触る前に `git status` と `git log` で差分と未 push を確認する
- 会話が長くなったら自動で要約し、原文は検索で取り戻せる状態に保つ

## 常駐の理由

差分の確認、検証コマンドの実行、デプロイの監視。どれも毎回手順が決まった作業です。それでも席に着かないと進められず、離れているあいだは作業が止まっていました。会話が長くなると前のやり取りを引き継げなくなるうえ、モデルを乗り換えるたびに同じ前提を書き直すのも手間でした。

そこで自宅サーバーにエージェントを常駐させ、こうした作業を移しました。エージェント自身はリポジトリを持ちません。SSH 越しに各マシンへ入り、ファイルを編集してコマンドを流します。

## Hermes Agent の構成

使っているのは Nous Research が公開している [Hermes Agent](https://github.com/NousResearch/hermes-agent) です。単体で動き続ける自律エージェントで、CLI・デスクトップアプリ・メッセージングのゲートウェイのどれから入っても、同じセッションの続きを話せます。組み込みツールは 60 以上。

外部の API をツールとして呼び出すための規格（MCP）にも対応していて、Cloudflare の設定確認のような操作も任せられます。手順は agentskills.io 互換のスキルとして貯められるので、同じ作業を毎回説明し直さずに済みます。使うモデルとプロバイダの差し替えは設定ファイルの編集だけです。

実行場所は Proxmox VE 上の LXC 1 台。systemd でゲートウェイを常駐させ、状態・会話ログ・記憶・スキルはプロファイルごとに分けたディレクトリ構成です。プロファイルは用途ごとの作業場で、履歴と手順が混ざらないので、同じマシン上で別々の文脈を同時に動かせます。

## SSH 接続の構成

`~/.ssh/config` の末尾に全ホスト共通の設定を置き、ControlMaster（同じホストへの接続を使い回す仕組み）と ControlPersist 10m で接続を多重化しました。1 セッションで何十回もコマンドを実行するため、接続のたびにハンドシェイクを繰り返すと待ち時間がかさみます。確認待ちで処理が止まらないよう `BatchMode=yes` も指定済みです。

エージェントには「まず `git status` と `git log` を読み、ブランチ違いと未 push を確認してから触る」という手順をスキルとして渡しています。接続先が複数あると、コマンドを実行したホストと報告するホストを取り違える事故が起きるため、ホスト名の対応表もスキル側に持たせました。

## モデルの選定基準

主力は DeepSeek V4.1 Flash。2026-08-11 から 91 日間で 155 セッションを処理し、1 日あたり 1.7 回、1 セッションあたり 51 メッセージ・26 回のツール実行という量です。reasoning effort（推論に使うトークン量の設定）は low に固定しています。

理由は 3 つ。ツール呼び出しの形式が崩れにくいこと、1 セッションあたりのコストが低いこと、応答が速いことです。

トークンの 95% 以上はキャッシュ読み出しで賄われています。キャッシュ外の入力が 2,521 万、キャッシュ読み出しが 5 億 5,233 万トークン。長いシステムプロンプトとスキルを毎回送る構成なので、キャッシュから読み出せるかどうかで実質のコストが決まります。

重い設計の相談では上位モデルを数セッションだけ使い、実装は Claude Code と Codex CLI に委譲するスキルを用意しました。エージェントは委譲先の出力をレビューし、テストとビルドを通してから報告します。

## 長い会話の圧縮

1 段目は組み込みの圧縮です。コンテキストの 50%、このモデルでは 65,000 トークンに達した時点で自動的に走ります。直近 20 メッセージは原文のまま残し、それ以前を 20% 程度まで要約します。

2 段目は Lossless Context Management のプラグイン。要約と原文の両方を残しておき、あとから全文検索で元のやり取りまで戻せる仕組みです。圧縮で消えた部分を、要約の階層と原文の両方の形でローカルのデータベースに残します。要約だけでは足りないときに、当時のメッセージをそのまま引けます。3 か月で 14.7MB、圧縮対象になったメッセージは 3,587 件です。

ツール出力が大きいときは、会話には参照 ID だけを残します。全文は必要になった時点で取得します。

要約の位置づけは「信頼しない履歴」です。指示として読み直さないようプロンプト側でも区切りました。圧縮したやり取りを現在の指示として解釈すると、過去の古い方針で現在の作業を上書きしてしまうためです。

## 状態の日次バックアップ

エージェントの状態は消えると復元できません。会話ログ、記憶、スキル、スケジュールを毎日 02:30 にまとめて退避しています。

- `hermes backup --quick` による全プロファイルのスナップショット取得
- スナップショットに含まれない会話データベースの、SQLite の backup API を使った一貫コピー
- プロファイルごとの tar.gz 化と、rclone の暗号化リモート（転送前に暗号化する保存先）経由での Google Drive への転送
- リモート 14 日・ローカル 2 日保持、cron の二重起動防止（flock）

## 事故と対策

常駐させてから、こちらの手順が原因で壊した箇所が 3 つあります。どれもスキルに書き戻したので、同じ形では起きなくなりました。

1 つ目は古いコピーを本物だと思ったこと。同じリポジトリの古いチェックアウトが別ホストに残っていて、そちらを見て「変更が反映されていない」と判断しかけました。いまは触る前にブランチと未 push を確認します。

2 つ目は自分自身のプロセスを止めたこと。`pkill -f` のパターンが実行中のシェルのコマンドラインにも一致し、セッションごと落ちました。プロセスを止めるときは PID を引いてから止める手順に変えました。

3 つ目は認証切れで止まったこと。トークンの期限が切れると、非対話の push は確認待ちのまま止まります。`BatchMode=yes` で即座に失敗させ、認証は人が更新してから再開する運用にしました。

## 委譲の範囲と手順

委譲しているのは、差分と履歴の確認、検証コマンドの実行、デプロイの監視、ログの調査まで。採用するか、push するか、公開するかは自分で決めています。

作業中につまずいた点はその場でスキルに書き戻し、次のセッションで同じ失敗を繰り返さないようにしました。モデルを乗り換えてもスキルと会話ログは残るので、手順を書き直さずに移行できます。
