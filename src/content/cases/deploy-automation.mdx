## 手作業のデプロイは、記憶と手順に頼るほど壊れる

手動でコマンドを叩いてデプロイしていた頃は、作業者ごとの手順の微妙な違いやコマンドの実行漏れがつきまとっていました。更新頻度を上げようとすると、それに比例して確認ミスへの不安が膨らむ状態でした。

## 抱えていた問題

- 手順が頭の中にしかなく、時間が経つと「どのコンテナをどの順序で再起動すべきか」を思い出すところから始まる
- 途中でエラーが出たとき、どこまで反映されて何が未完了なのかを追いにくい
- 個人開発であっても、更新のたびに手順書を開いて手動確認するのは負荷が大きかった

## GitHub Actions と自宅 runner による自動化

更新処理を人の記憶に委ねないよう、GitHub Actions と自宅 Proxmox 上の self-hosted runner を組み合わせた CI/CD パイプラインを組みました。

`main` ブランチに push すると、まず GitHub 側で Lint・テスト・型チェックが走り、Docker イメージがビルドされて GHCR（GitHub Container Registry）へ送られます。続いて自宅サーバーの runner が更新を検知し、Compose ファイルの定義に従ってローカルのコンテナを更新します。

すべての手順をコード化（`.github/workflows/deploy.yml`）したことで、手元のターミナルから直接本番環境へ触る必要がなくなりました。

## 反映の迷いが消え、復旧の起点が揃った

更新の手間が `git push` だけに圧縮されたため、細かな修正をこまめに本番へ届ける心理的ハードルが下がりました。

副産物として大きかったのは、障害時の切り分けが格段に楽になったことです。ビルドログやコンテナログが自動で残るため、「何時から何が壊れているのか」の原因究明がログの確認から迷わず始められるようになりました。

## 自動化の価値は「速さ」より「判断の一貫性」にある

デプロイ自動化というと作業時間の短縮に目が行きがちですが、本質はそこではありませんでした。誰がいつ実行しても全く同じ手順と検証が適用される、その一貫性こそが精神的な負担を軽くしてくれます。
